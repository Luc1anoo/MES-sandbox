# 需求工单

## 需求评估与落地边界

需求的匹配、草稿、确认、评审和归档链路合理。实现时补充了以下规则：

- 工段为新增 Section 主数据，群组通过独立映射归属工段，不改写原 ProcessFlow 层级。一个群组属于至多一个工段。工序模板匹配采用现有 OperationCard ID（逻辑工序），执行工单绑定具体 Step ID。不能用同名文本作为唯一标识。
- 模板范围只允许：工序；群组＋工序；工段＋群组＋工序。空值代表任意。多个范围取该模板匹配的最高精度，不重复计票。同精度不同模板必须由需求人选择；未匹配不自动回退。
- 工单是订单＋Step 唯一记录。模板内容、适用范围、属性、是否评审都快照保存；修改/停用模板不影响已发工单。已使用模板不能物理删除。
- “工单传递完成”与“允许生产”分开：reviewing 表示已发起传递，但不代表评审通过。production 必须所有必需工单 confirmed 或 approved。
- 评审必须由需求人、工序责任人、专家三个独立账号执行。任一拒绝即 rejected；需求人修改后重新发起，旧轮次意见保留在审计事件中，新一轮三人重新评审。已确认/通过的工单不可原地修改。
- 订单进入工序设计后冻结其共享工艺路径，已有工单的工序策略/工段映射也不能修改。通过克隆新 Revision/Flow 新建订单处理变更，避免归档内容与实际路径错位。
- 通知是数据库内的站内待办，非邮件、短信或企业聊天推送；无提醒计划或离线推送。通知与工单状态在同一事务中保存，进入同一阶段重复提交不重复发通知。
- 当前只实现订单阶段管理、BOM 原文件上传、工单传递和生产前置检查，不解析 BOM、不调度设备、不执行生产。归档纪要为可在线阅读的结构化记录，包含模板快照、实际内容、意见、时间和参与人；不是数字签章/PDF服务。

## 使用

1. 更新代码，激活后端虚拟环境，从 backend 运行 `python migrate_workorders.py`，然后重启后端。前端运行 `npm run dev`，或重新构建部署。
2. 从「需求工单中心」为需求人（产线 Owner）、执行人、专家分别注册登录账号。密码至少 8 位。账号不设置默认密码。
3. 在「工段与工序属性」新增工段、设置群组归属，配置具体 Step 是否需要工单、加工/检测类别和责任人。工序必须已绑定工序卡；已发布工艺不可修改这些属性，应先克隆 Draft。
4. 「工单模板」新增加工或检测模板，配置是否评审、启用状态、多个适用范围及属性。可以添加、编辑、停用或删除未使用模板。
5. 「订单与工艺流」创建订单，指定 Flow、Owner、专家。Owner 上传 BOM 后依次推进：工艺设计 → 工序设计。进入工序设计时创建工单并通知 Owner。
6. 若匹配到唯一最高精度模板，自动快照；若冲突，打开工单选择弹框中最高精度候选。无匹配时先维护模板，然后刷新并选择。
7. Owner 填写、保存草稿，或按模板要求确认/确认并发起评审。无需评审的确认会通知执行人；需评审时通知三方，三方分别登录给出结论和必填意见。
8. 在工单内查看归档纪要，复制 `?workorder=ID` 链接；参与人登录后可访问。不公开暴露附件或纪要。
9. 原 Flow Designer 增加订单选择框，工序卡上显示 `! 工单传递未完成` 或评审/确认状态。「订单与工艺流」也显示对应的工序状态。原设计器必须登录工单中心后才能查看订单级状态，按刷新或最多15秒更新。

## 属性

支持 text、number、quantity、coordinate、select、multi_select、status、date、person、created_time、created_by、edited_time、edited_by、files、url、email、phone。

- quantity 数据为 `{value:200,unit:"nm"}`；单位在模板中确定，服务器不隐式换算。
- coordinate 数据为 `{values:[1,2,3],unit:"um"}`；模板确定2D或3D和单位。
- number 支持 decimal/percent/currency 展示格式；percent 存储用户输入的显示数值（95表示95%），不自动转换为0.95，currency 为格式标识，不进行汇率换算。
- 单选、多选、Status 只能取模板选项。Status 可以额外配置分组 JSON，例如 `{"进行中":["Learning"],"完成":["Done"]}`，必须覆盖所有选项且不重复。属性 Status 与工单审批状态互相独立。
- Date 填 `YYYY-MM-DD`，或 `YYYY-MM-DD 至 YYYY-MM-DD`。后端校验实际日期及范围先后顺序。
- Person 必须是已注册成员 ID；创建/修改人员及时间由服务器维护，不接受客户端伪造。
- Files 上传原文件，单文件最大10MB，不限文件扩展名；作为 attachment 下载，使用随机存储名，不执行或内嵌渲染。没有杀毒扫描或总量配额。
- 保存草稿允许缺少必填值，但已填写字段仍校验格式；确认/发起评审时检查所有必填值。

## 数据、认证及部署

所有新增表使用 `wo_` 前缀，独立 StepPolicy 保留原 Step 表和数据不变。迁移只创建缺失表，可重复执行；新启动的 create_all 也会注册新增表。升级前应备份 SQLite 和附件目录。已有历史缺列仍需先运行原来的迁移；本脚本不修复已有错误结构。

附件默认保存在仓库 `.workorder-files/`（已忽略），可用 `MES_WORKORDER_FILES` 指定持久目录。部署与备份必须包含该目录；只保存数据库不能恢复附件。

新增模块使用 scrypt 密码摘要、随机 Bearer 登录令牌（数据库仅存摘要）、12小时有效期、退出失效；工单读写、附件与归档检查参与人。模板/工艺配置允许所有已登录成员维护，未增加企业管理员角色。原 MES API 仍没有统一认证，本功能不是全项目的生产安全改造；上线前应接入企业身份和权限体系、HTTPS及账号管理。

模板编辑、工单修改/评审携带 revision，旧页面提交返回409，需刷新；阶段跳转按顺序校验。新增账号目录与原 OperationCardVersion.responsible_person 的自由文本不是同一字段，工单策略中需显式选定责任账号。

主要 API 前缀 `/api/workorders`：register/login/logout、members、sections、groups/{id}/section、steps/{id}/policy、templates、orders、orders/{id}/stage、tickets、tickets/{id}/template、tickets/{id}、tickets/{id}/vote、tickets/{id}/archive、notifications、notifications/{id}/read、files。所有工单业务 API（注册/登录除外）需要 Bearer token。

测试：从 backend 执行 `python -m pytest -q`，包括原功能与工单生命周期、冲突选择、模板快照、阶段检查、三方拒绝/重审、附件权限、类型校验、路径冻结和增量迁移。浏览器冒烟使用独立临时数据库。
